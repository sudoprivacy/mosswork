# 企业客户端设备凭证原地续约方案

设计基线：官方 `main` 提交 `084b8a186a5f918e08881826af294d226ce981ee`。适用于走员工 JWT 配对、通过原生设备通道执行本地任务的企业客户端。

实现说明：下文保留设计时的备选字段。实际协议使用「短票 + 候选密钥摘要」标识一次兑换，不另加请求 ID 或数字凭证代次；数据库对当前摘要做条件更新。在线兑换使用原连接，离线恢复使用独立的 `recover` 首帧。请求已被服务端接受但应答丢失时，可以确认同一候选的结果，不能用同一张票重复延长期限。

## 1. 目标和不承诺的情况

**用户在正常使用客户端时，不应因为跨过设备凭证的 8 小时边界，被迫重新登录、重复发送消息或重做任务。** 保留短期凭证，不设永久令牌。员工登录仍有效、设备仍被授权、续约在硬截止前完成时，在原连接上换用下一张凭证。正在运行的本地进程、任务、目录授权和已打开的模型流不动。

验收示例：设备原定 17:00 到期，在一个文档任务和一次工具调用均已开始后完成续约；越过 17:00 继续执行，仅产生一个 Word 文件，原会话收到同一任务的一份结果，随后无需登录即可发下一条消息。任务本身的执行超时、用户取消和管理员撤权仍然有效。

这不是断电恢复或任意断网时不中断的承诺。若用户退出、账号禁用、设备被撤销或长时间离线导致任何有效授权都不存在，不得后台复活设备。已有结果按[企业客户端恢复规则](../enterprise-client.md)处理；结果未知的操作不自动重放。原截图是通用断连提示，不作为已证实的到期故障统计。

## 2. 为什么只改服务端有效期不够

| 基线中的实际行为 | 不改的后果 |
| --- | --- |
| [设备管理器](../../src/octop/infra/devices/manager.py)的 `issue_pairing` 取 `min(now + 8h, JWT.exp)`；配对码最长 120 秒。心跳只更新 `last_seen_at`。 | 登录 JWT 的滑动续期不延长已配对的设备；仅调大账号 TTL 或发送更多心跳无效。 |
| [桌面工作区上下文](../../dashboard/src/context/DesktopWorkspaceContext.tsx)只在初始化或手动重试时尝试配对；[原生配对入口](../../desktop/src/workspace.go)会先调用 `stopCompanyRuntimeLocked` 并更换设备客户端。 | 把“重新配对”挂在定时器上，会主动停掉要保护的任务，也可能改变设备 ID 和授权。 |
| [Go 设备客户端](../../desktop/src/internal/company/client.go)在 `serveFiles` 上固定连接 deadline，重连还要求 `ExpiresAt` 与首次握手相同；[运行时看门狗](../../desktop/src/company_runtime.go)按启动时传入的 `expires` 停掉子进程。 | 即使数据库里的时间已经更新，桌面仍会按旧时间断开或杀进程。 |
| [设备任务](../../src/octop/infra/devices/tasks.py)与 `manager.py` 的单次 `call` 均有期限，创建时被设备旧期限截短；Go 对已接收的 `call` 再创建固定 deadline。 | 只让连接和进程活着，已经发出去的文件操作仍可能被旧期限取消。 |
| [Python 运行时](../../src/octop/infra/company_runtime/runtime.py)仅在 `initialize` 时装入凭证；[HTTP 客户端](../../src/octop/infra/company_runtime/client.py)把它写入默认请求头，模型流也使用此客户端。 | 只换 Go 侧凭证，运行中的 Python 下一次查权限、开模型流或回传结果仍会用旧凭证。 |

## 3. 推荐设计：账号确认，原设备兑换

不要让单独一张设备凭证靠心跳无限给自己续期，也不要把账号 JWT 交给本地工具。复用签入工作台与原生设备通道两个已有授权边界。下列接口、帧和数值除现有 8 小时上限外均是提议，不是现有 API。

1. **协商和触发。** 新服务端在现有 `ready` 响应中附带可选续约能力；新客户端在收到能力声明、且桌面桥和配套本地运行时支持后，主动发送 `lease_enable`，双方确认后才按新语义发起任务。在旧端严格校验的首个 `hello` 中不加新字段，不向旧客户端推新帧。协商不改写已按旧协议启动的调用；升级不承诺接管旧进程。由原生时钟安排一次续约，到期前预留 `min(15 分钟, 本次有效时长 / 3)`；恢复网络、系统唤醒或窗口恢复时重新判断，不依赖用户打开设置或再发一条消息。按设备和登录会话保持一个在途续约，失败时退避并加抖动。
2. **工作台取得短期续约票。** 建议 `POST /api/devices/{device_id}/renewal-ticket`。用当前员工 Bearer 鉴权；从实际请求 JWT 取 owner、稳定登录 `sid` 和 `exp`。签发前核对设备归属、相同 `sid`、未撤销且未到期；票据仅用于指定设备和当前凭证代次，建议最长 60 秒、单用，不是设备凭证。响应 `no-store`。如当前 JWT 剩余不足以延长设备授权，先通过现有鉴权请求接收滑动续签响应头，再用**新 JWT** 取票；没有更晚的授权期限就不轮换，不忙循环。换账号、退出或同一用户重新登录后，旧页面的异步回调无效。首版不借此开放当前员工配对不支持的身份模式。
3. **原设备在现有 WebSocket 兑换。** WebView 只经现有 origin/nonce 校验的桥传短票。Go 在内存中生成新随机设备秘密，保存候选值，发送短票、候选秘密摘要、预期代次和请求 ID；服务端从当前已认证连接取得设备身份。事务内验证票、登录、账号、设备和当前代次后，消费票并推进凭证代次。新期限为 `min(服务端当前时间 + 8 小时, 本次已验证 JWT.exp)`，必须晚于旧期限。更新原设备行和现有连接，不调用 `pair`、`connect_device` 或重建目录授权。**凭证代次**与用于隔离旧连接回执的 **连接代次** 分开；正常轮换不改变后者。
4. **可恢复的交接。** 服务端返回请求 ID、新代次和新到期时间；Go 使用这个确认同时更新连接、原生 HTTP 调用和运行时。提供短暂交接窗口（建议最多 60 秒且不越过旧凭证原到期点），用来接住已构造的旧请求；旧凭证不再有新一轮续约权。已通过鉴权的正常长流不因密钥更换而被主动关闭。服务端能按同一请求 ID、同一候选摘要返回同一结果，不重复延长；Go 保留候选直到结果明确，即使确认丢失也能用候选核对已提交结果。只有仍是同一设备和登录时才可恢复；撤销始终优先。建议将活动/交接摘要、版本和有限期兑换记录存于数据库，绝不存明文；比较并更新须在 SQLite、PostgreSQL 上都具备同样的并发语义。
5. **失败分类。** 到期前遇到瞬时网络故障，继续用最后确认且未过期的授权，后台重试，不因一次续约失败而停任务。过了硬截止且无法证明续约已提交，停止特权操作，不猜测在途工具结果。区分“网络重连中”“设备授权已失效”“账号需重新登录”；仅账号鉴权确实失效才走页面的登录失效处理。账号退出沿用[已有注销、会话和设备撤销](../../src/octop/api/routers/auth.py)，同时使该会话的待用票据和交接凭证失效；不能靠过期前发出、退出后才到达的响应恢复权限。

### 硬到期后的重新授权

同一次登录仍有效、设备未撤销且原生进程还持有设备证明时，可自动获得新的短票，以 `recover` 首帧提交短票、原设备证明和候选密钥摘要。服务端验证后更新原设备，而不是创建第二个配对。真正断线后建立新的连接代次；中断任务不重放。短票响应携带每票不同的密钥识别提示（不是凭证），用于分辨提交成功但确认丢失的候选密钥。无有效登录、设备证明或匹配身份时，不能走此路径。

## 4. 在途任务的改动清单

| 层 | 必须实现的行为 |
| --- | --- |
| 服务端设备通道 | 用经验证的当前租约替代 `serve` 闭包中的首次 `row` 快照；更新同一个 `Connection`。保持 socket、`generation`、`pending`、`call_id` 和 `grant_version`。设交接顺序屏障：在客户端确认已采用新租约前，不下发要求新租约才合法的帧。HTTP、WS、回执和多进程归属路由读取一致的授权状态；事务不跨网络等待。 |
| Go 桌面 | `Client` 统一持有可动态读取的租约、凭证代次与撤销状态；连接循环、重连校验、`RuntimeIdentity`、原生 HTTP 和 `watchRuntimeIdentity` 均读取它。以可更新截止的租约守卫替代首次握手的 `context.WithDeadline`，不能用取消旧父 context 的方式更新时钟。确认匹配原设备、账号、会话及本地实例后才应用；迟到的旧确认不得回滚状态。正常轮换不更换进程，不调用第二次 `initialize`。 |
| 已开始的设备任务 / 文件调用 | 协商成功的链路中，将任务本身的绝对超时（例如 `DeviceTask` 创建后 1 小时）、调用业务超时与动态设备授权分开表示。执行条件是“业务尚未超时 **且** 当前租约有效 **且** 目录授权仍有效”。Go 的在途 `callCtx` 不应冻结旧凭证到期点，由业务计时器和可撤销的租约父级共同约束；服务端对应更改 task、wire `call` 的期限和校验。硬到期无续约仍须取消。旧协议保持原规则。绝不为了续约重发 `call`。 |
| Python 本地运行时 | 在[私有 stdio IPC](../../src/octop/company_runtime.py)增加原生专用的凭证切换消息及确认，不加入网页 runtime RPC 白名单。每次新建请求（含模型流、上传、结果同步）取当前凭证快照；不关闭共享 HTTP 客户端，不中止已打开的流，不重试已发送的有副作用请求。处理运行时尚未启动、正在初始化、正在工作三种时序；初始化和轮换串行交接，较旧版本不能覆盖较新版本。IPC 确认丢失可按版本重复通知，但不重新执行任务。 |
| 工作台与诊断 | 扩展[桌面桥类型](../../dashboard/src/api/desktopWorkspace.ts)和工作区上下文，传递能力、续约需求和结果而不是设备秘密；不复用 `retry → pair`。绑定稳定会话身份而非只看用户 ID，避免 JWT 滑动更新触发重新配对。前后台分别保留网络故障、撤销、到期和客户端不兼容原因。仅记录结果类别、剩余时间区间、重试数；不记录短票、凭证、JWT 或文件内容。 |

## 5. 实施顺序与兼容

| 阶段 | 交付及放行条件 |
| --- | --- |
| 1. 服务端协议与存储 | 扩展 [devices 路由](../../src/octop/api/routers/devices.py)、[协议模型](../../src/octop/infra/devices/protocol.py)、领域管理器和 [DeviceRepo](../../src/octop/infra/db/repos/devices.py)。显式建模取票、兑换、重复确认与拒绝；双数据库成对迁移，编号按实施时已发布水位确定，不修改已应用的旧迁移。旧客户端不启用新语义。先通过鉴权、撤销竞态及幂等测试。 |
| 2. 桌面与运行时 | 实现可更新租约、原生调度、私有 IPC 和业务超时拆分。双端协商完成前不走新路径。用可控时钟跑过旧截止点，并证明同进程、同任务、同连接代次和操作只执行一次。 |
| 3. 工作台与端到端 | 接入取票、会话隔离和错误提示，中英文同步。不在 React 轮询中无条件发请求。覆盖休眠唤醒、窗口最小化、长流及配置的短 JWT 有效期。服务端、桌面、Python 单测通过不代替实机组合验收。 |
| 4. 分步启用与回退 | 部署顺序建议先兼容服务端，再验证配套工作台及完整原生客户端。旧服务端 + 新客户端、新服务端 + 旧客户端均维持原固定期限，不因未知帧断开。回退应先停止签发新续约票，让已签发授权自然结束或明确撤销；不要在活动连接上强制重新配对。正式构建、官方 COS 清单更新和版本变更另行安排；不通过 Python 在线自更新分发。 |

## 6. 验收与发布阻断项

| 场景 | 可观测断言 |
| --- | --- |
| 正常跨期，连续两轮续约 | 利用假时钟/测试签发器，不必等待 8 小时，也不新增生产环境的短 TTL 开关。先启动文档任务和一次受控写入，再触发续约，跨过原截止点后取回结果、继续下一轮对话。记录并比对设备 ID、连接代次、目录授权、运行时 PID、任务 ID、操作 ID；业务写入一次，终态回执一次。 |
| 已开流与待审批 | 已开的模型流不中断，轮换后下一次 HTTP 请求使用新凭证；审批在旧截止后仍能批准或拒绝原任务。业务自身到期或用户取消时仍按原规则停止。 |
| 请求或确认丢失、并发 | 丢弃兑换确认、重复提交、并发刷新、乱序 IPC、重连到所属 worker。幂等返回同一代次；正常续约不改变连接代次，真实重连仍执行原有连接隔离；不重发正在写文件的工具操作。 |
| 失效与撤权 | 登出与兑换并发、禁用账号、撤销设备/目录、同用户新登录、跨账号/设备短票、过期票、旧密钥交接结束；不能扩大授权或复活旧设备。仅有设备凭证或仅有短票都不能续约。 |
| 断网与版本混用 | 短暂网络波动不触发无条件重新配对；休眠超过硬截止不静默续活。已完成待同步的结果只补传，结果未知保持待核对。覆盖两个方向的混合版本，以及 `targets.json` 定义的 Windows amd64、macOS arm64 完整客户端。 |

实施时优先扩充 `tests/unit/devices/`（票据、设备任务和 HTTP）、`tests/unit/company_runtime/`（HTTP/流、stdio、恢复）、`desktop/src/internal/company/` 与桌面运行时测试、`dashboard/src/context/DesktopWorkspaceContext.test.tsx` 与 `dashboard/src/api/desktopWorkspace.test.ts`。示例定向检查：
