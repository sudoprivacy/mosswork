# mosswork 资源市场试用操作手册

本文面向第一次试用 mosswork 资源市场的管理员、现场开发人员和普通使用人员。本文描述当前版本已经实现的操作流程：**导入资源包 → 管理员审核发布 → 用户查看专家或技能 → 创建专家或安装技能包 → 挂载技能包到专家**。

本文中的“市场”是 mosswork 部署内置的本地市场，不依赖腾讯技能市场或公网服务。实际访问地址由管理员提供，例如 `http://127.0.0.1:8091`。

## 默认随包携带的资源

首次启动时，mosswork 会把仓库内置专家库中的资源转换为本地资源市场的正式版本，并自动完成“已发布、已上架、已推荐”初始化。当前随包内容为 **18 个专家和 42 个技能，共 60 个资源**；专家引用的内置技能会自动锁定到对应的 `1.0.0` 版本。该初始化在每次启动时幂等执行，不会重复创建，也不会覆盖客户后来创建的同名资源。

这些默认资源不需要访问腾讯 SkillHub，客户部署后即可在“专家 → 专家市场”和“技能包 → 资源市场”查看、创建或安装。资源市场中的版本、摘要、依赖和安装记录仍按普通正式版本处理，因此后续可以由管理员继续导入同一资源的新版本。

本发行包同时携带一份构建期生成的 SkillHub 离线快照，启动时只读取本地文件，不访问外网。快照中的资源由维护者在发布前完成来源和再分发审核；后续刷新快照时也必须重新完成这项审核。客户如果要加入自己的外部资源，应通过资源市场导入已获授权的 ZIP 包。

已提供构建期快照工具 `tools/fetch_skillhub_snapshot.py`。执行后会分页读取 SkillHub 的专家技能集，并读取技能市场的公开搜索目录和榜单目录，合并去重后下载技能 ZIP、专家图标和来源索引到 `src/octop/infra/market/skillhub_snapshot/`。启动时只读取这些本地文件，不访问外网。外部资源使用 `skillhub-expert-*` 和 `skillhub-skill-*` 标识，避免覆盖原有内置资源或客户资源。

快照会区分“已下载并可发布”和“目录存在但包缺失/内容不合规”。当前快照包含 54 个专家目录和 2,676 个技能目录条目，其中 48 个专家包、2,646 个技能包通过本地包校验；6 个专家和 30 个技能因缺少可下载包只保留在索引中，不会发布不完整版本。后续刷新快照时数量会随 SkillHub 上游目录变化。图标按原始格式随专家包离线保存，资源市场和从专家创建 Agent 时使用本地 `/api/experts/market/{version_id}/icon` 地址。

## 一、先理解三类角色

| 角色 | 可以做什么 | 常用入口 |
| --- | --- | --- |
| 管理员 | 导入资源包、审核发布、设置推荐版本、上架或下架资源 | 资源市场 |
| 现场开发人员 | 准备专家或技能 ZIP 包，导入为自己的草稿并提交审核 | 资源市场 |
| 普通使用人员 | 查看已发布专家、创建自己的专家；查看已发布技能、安装技能包并挂载到专家 | 专家、技能包 |

权限由管理员分配。如果登录后看不到某个菜单，通常是账号没有对应权限，并不代表资源不存在。

试用时建议使用三个账号验证权限边界：一个管理员账号、一个拥有资源市场提交权限的开发账号、一个只拥有专家使用和技能包权限的普通账号。

## 二、试用前准备

管理员需要先确认以下事项：

1. mosswork 服务已经启动，浏览器可以打开管理员提供的服务器地址。
2. 管理员账号可以登录。
3. 用于创建 Agent 的模型或 Provider 已配置并可用。资源市场本身可以离线浏览和安装，但真正开始对话仍需要可用模型。
4. 现场开发人员已经准备符合规范的 ZIP 包，或使用资源市场中的技能模板、专家模板开始开发。
5. 如果要测试技能挂载，普通用户需要 `技能包` 权限；如果要测试发布流程，开发人员需要资源市场提交权限，管理员需要资源市场管理权限。

## 三、管理员发布一项资源

### 3.1 打开资源市场

登录后，在左侧打开“资源市场”。资源市场页面可以看到资源名称、类型、推荐版本、版本数量和上架状态。

资源分为两种：

- **专家**：用于创建 Agent，包含角色定义、工作流程和欢迎语等内容。
- **技能**：用于加入技能包，再挂载到一个或多个专家。

### 3.2 导入 ZIP 包

点击“导入资源”，选择技能 ZIP 或专家 ZIP。导入后会先生成一个草稿，不会立即出现在普通用户的市场中。

导入窗口会提示包的基本要求：

- 技能包必须包含 `market.json` 和 `SKILL.md`。
- 专家包必须包含 `market.json`、`manifest.json` 和 `SOUL.md`。
- ZIP 和展开后的文件总量不能超过 64 MiB，文件数不能超过 2000。
- 文件必须使用 UTF-8，不能包含绝对路径、父目录跳转、符号链接、凭据、个人数据、`.env`、Git 目录或会话文件。
- Finder、Windows Explorer 或 Linux 文件管理器可能自动加入 `__MACOSX/`、`._*`、`.DS_Store`、`Thumbs.db`、`desktop.ini`、`.directory`、回收站目录等压缩元数据。导入器会自动忽略已知的跨平台文件管理器元数据，不需要手工打开 ZIP 删除；真正的隐藏文件、个人资料、凭据和运行依赖目录仍会被拒绝。建议把 `market.json`、`manifest.json`、`SOUL.md` / `SKILL.md` 放在 ZIP 根目录。
- 包内脚本只会作为文件保存和预览，导入、审核和安装过程不会自动执行脚本。

导入后先查看文件清单、声明、运行环境、依赖和现场配置说明。资源市场不会把“声明”自动变成权限，也不会替开发者安装 Python、Node 或其他运行环境。

#### `market.json` 是什么格式

`market.json` 是资源包根目录中的**资源声明文件**，用于告诉市场“这是什么资源、是什么版本、需要什么运行条件和依赖”。它不是技能执行代码，也不保存现场密码、Token 或业务系统的真实地址。文件必须是 UTF-8 编码的标准 JSON：字段名和字符串使用双引号，不能写注释，也不能增加规范之外的字段。

技能声明示例：

```json
{
  "format": "mosswork.market.v1",
  "kind": "skill",
  "slug": "equipment-query",
  "name": "设备状态查询",
  "description": "查询厂内设备实时状态",
  "version": "1.0.0",
  "changelog": "首次发布",
  "dependencies": [],
  "runtime": {
    "execution_targets": ["server"],
    "platforms": ["any"],
    "python": ">=3.12",
    "runtime_profile": ""
  },
  "configuration": {
    "business_api_url": {
      "type": "url",
      "required": true,
      "description": "现场设备系统接口根地址"
    },
    "credential_binding": {
      "type": "credential_ref",
      "required": true,
      "description": "设备系统凭据引用"
    }
  },
  "required_capabilities": [],
  "network": {"scope": "intranet"},
  "license": "MIT",
  "author": "现场开发组"
}
```

主要字段含义如下：

| 字段 | 填写规则 |
| --- | --- |
| `format` | 固定填写 `mosswork.market.v1`；也兼容 `octop.market.v1`。 |
| `kind` | `skill` 表示技能，`expert` 表示专家。 |
| `slug` | 资源唯一短标识，只能使用小写字母、数字和连字符，且以小写字母开头，例如 `equipment-query`。技能的 `SKILL.md` 中 `name`、专家 `manifest.json` 中 `id` 必须与它一致。 |
| `name` / `description` | 面向用户显示的名称和说明，不能为空。 |
| `version` | 严格使用三段版本号，例如 `1.0.0`、`1.1.0`；发布新版本时递增版本号。 |
| `changelog` | 本版本更新说明，不能为空。 |
| `dependencies` | 依赖的已发布技能列表，每项写 `resource_id` 和精确 `version`；没有依赖时写 `[]`。 |
| `runtime` | 运行目标和环境要求。常用服务器资源填写 `execution_targets: ["server"]`、`platforms: ["any"]`。这些字段只做声明，不会自动安装环境。 |
| `configuration` | 现场需要提供的配置项定义，只写类型、是否必填和说明，不写真实值。类型支持 `string`、`url`、`integer`、`boolean`、`credential_ref`。 |
| `required_capabilities` | 所需能力声明，不等于授权；当前通用安装器应填写 `[]`，非空能力需要先完成运行适配。 |
| `network` | `none` 或 `intranet`。局域网业务系统通常填写 `intranet`，第一版不接受公网依赖声明。 |
| `license` / `author` | 资源许可和作者信息。第三方内容必须遵守其原始许可。 |

专家的 `market.json` 使用同一套字段，只需把 `kind` 改为 `expert`，并将 `slug` 与专家包中的 `manifest.json` 的 `id` 保持一致。专家包还必须提供非空的 `SOUL.md`。首次导入时通常不填写 `resource_id`，由服务器创建；后续版本应通过原资源的“导入新版本”操作提交，并保持 `kind` 和 `slug` 不变。

需要特别注意：系统不会仅凭 ZIP 中的 `slug` 自动把一次普通导入归并到历史资源。首次导入不填写 `resource_id` 时，服务器会创建新的资源身份；如果该 `slug` 已经存在，导入会被拒绝。更新已有资源时，必须从该资源详情中点击“导入新版本”，由页面带上原资源的 `resource_id`，服务器再同时校验 `resource_id`、`kind` 和 `slug` 是否一致。这样可以避免同名资源覆盖或误归并。

专家声明示例只需将资源类型改为 `expert`，并声明它依赖的已发布技能：

```json
{
  "format": "mosswork.market.v1",
  "kind": "expert",
  "slug": "equipment-inspector",
  "name": "设备巡检专家",
  "description": "根据设备状态生成巡检结果和异常说明",
  "version": "1.0.0",
  "changelog": "首次发布",
  "dependencies": [
    {"resource_id": "equipment-query", "version": "1.0.0"}
  ],
  "runtime": {
    "execution_targets": ["server"],
    "platforms": ["any"],
    "python": ">=3.12",
    "runtime_profile": ""
  },
  "configuration": {},
  "required_capabilities": [],
  "network": {"scope": "intranet"},
  "license": "MIT",
  "author": "现场开发组"
}
```

对应的 `manifest.json` 至少要有 `id`，并且值必须与 `slug` 相同；实际角色和工作流程写在 `SOUL.md` 中：

```json
{
  "id": "equipment-inspector",
  "label": {"zh": "设备巡检专家", "en": "Equipment Inspector"},
  "description": {"zh": "设备查询、异常分析与巡检报告", "en": "Equipment inspection and reporting"},
  "prompt_files": ["SOUL.md"]
}
```

### 3.3 提交审核

确认草稿内容后，点击“提交审核”。提交会冻结当前内容和摘要，后续不能直接修改这份草稿；需要修改时应重新导入新草稿。

提交后，实际管理员打开草稿，检查：

- 名称、版本号和更新说明是否正确。
- 文件清单是否包含敏感信息或无关文件。
- 技能依赖是否指向已发布且仍上架的技能版本。
- 运行环境、业务系统地址、凭据引用和能力声明是否与现场实际情况一致。
- `SOUL.md`、`SKILL.md` 是否说明触发条件、输入、输出、异常处理和操作边界。

### 3.4 发布、推荐和下架

管理员审核通过后点击“审核并发布”，资源才会进入正式市场。

- 第一个正式版本会成为推荐版本。
- 后续版本不会自动替换推荐版本，管理员需要明确点击“设为推荐”。
- 下架只会阻止新的查看和安装，已经创建的 Agent 或已经安装的技能包不会被删除。
- 正式版本不可覆盖。相同资源需要更新时，应导入新版本，例如从 `1.0.0` 导入 `1.1.0`。

## 四、普通用户从专家市场创建 Agent

### 4.1 查看发布版本

1. 登录普通用户账号。
2. 打开左侧“专家”。
3. 切换到“专家市场”。
4. 点击专家卡片查看详情。

详情页会显示固定的发布版本、文件预览和技能依赖。这里展示的是管理员发布的本地版本，不会查询腾讯市场或公网市场。

### 4.2 创建自己的专家

在详情页点击“从此版本创建 Agent”，填写：

- 专家名称。
- 使用的模型或 Provider。
- 工作区或存储位置。
- 当前账号有权限使用的知识库、连接器和其他配置。

发布包中的专家定义和固定技能依赖是只读的。创建成功后，Agent 会出现在“我的专家”中；按照页面提示绑定 Provider 并启动，然后才能开始对话。

创建时系统会重新校验资源包摘要和全部固定依赖。如果依赖下架、包内容损坏、依赖版本冲突或运行环境不支持，创建会失败，不会留下半成品 Agent。

当前第一版创建器支持通用服务器资源：运行目标需要包含 `server`，平台需要包含 `any`，并且不能声明当前安装器尚不支持的 Python 版本、运行时配置、必填现场参数或能力要求。遇到这类提示，应联系开发人员调整资源声明或完成运行适配。

## 五、普通用户从技能市场安装技能

技能的完整使用链路分为两步：先安装成技能包，再挂载到专家。

### 5.1 打开技能市场

有两种入口：

- 打开左侧“技能包”，点击“资源市场”。
- 打开某个专家，进入“技能”页签，点击“资源市场”。

普通用户只需要技能包使用权限，不需要资源市场发布权限。页面会列出管理员已发布且仍上架的推荐技能版本。

### 5.2 查看技能详情和版本

点击技能卡片的“查看详情”，可以查看：

- 技能说明和更新说明。
- 技能文件预览。
- 本次安装包含的技能和全部固定依赖。
- 当前技能版本和同一资源的历史正式版本。
- 资源摘要，用于确认安装的是哪一份正式包。

如果需要安装历史版本，在“版本”下拉框中选择具体版本。安装请求会使用选定的 `version_id`，不会因为管理员后来修改推荐版本而改变。

### 5.3 安装到技能包

1. 在详情页确认版本和依赖。
2. 输入一个新的技能包名称，例如“设备巡检清单 v1.1.0”。
3. 点击“安装到技能包”。
4. 等待页面提示安装成功。

安装会创建一个独立技能包，包含所选版本和全部固定依赖。系统会先完整暂存并校验内容，成功后才让技能包出现在列表中。

以下行为会被阻止：

- 使用已经存在的技能包名称覆盖原包。
- 安装已下架或不存在的版本。
- 安装摘要校验失败或依赖不完整的资源。
- 安装声明了当前安装器不支持的运行环境或必填配置的资源。

安装成功后，技能包详情会显示“市场来源 vX.Y.Z”。这表示最初安装的正式版本；技能包后续允许按权限本地编辑，但编辑不会修改市场正式版本。

### 5.4 挂载到专家

安装技能包后，打开要使用该技能的专家：

1. 进入“技能”页签。
2. 打开“技能包”页签。
3. 找到刚安装的技能包。
4. 打开技能包右侧的挂载开关。
5. 返回专家对话，开始新任务验证技能是否生效。

如果当前专家的存储后端不支持直接挂载技能包，页面会提示使用“复制技能”将技能复制到该专家工作区。复制后是独立副本，后续市场版本不会自动覆盖它。

同一个专家不要同时挂载包含同名技能的多个版本，否则可能产生技能来源冲突。升级技能时，建议先安装新版本技能包，确认内容后再替换专家的挂载关系。

## 六、版本更新怎么做

### 6.1 更新专家

1. 开发人员基于原资源导入新版本，例如 `1.1.0`。
2. 管理员审核并发布。
3. 管理员根据需要把新版本设为推荐。
4. 用户在“专家 → 专家市场”查看新推荐版本。
5. 用户从新版本重新创建 Agent，或由管理员按后续升级流程处理。

当前版本不会自动改写已经创建的 Agent，也不会自动把旧对话切换到新专家定义。原 Agent 和原对话继续保留原来的版本；需要使用新版本时，应创建新的 Agent 并进行验证。

### 6.2 更新技能

1. 开发人员导入技能的新版本。
2. 管理员审核、发布并按需设置推荐版本。
3. 用户在技能市场选择新版本并安装为新的技能包，例如“设备巡检清单 v1.1.0”。
4. 用户在专家的“技能 → 技能包”中替换挂载关系。
5. 确认新技能工作正常后，再取消旧技能包挂载。

市场发布、推荐和下架不会自动修改已经安装的技能包。

## 七、常见问题

| 现象 | 原因和处理方式 |
| --- | --- |
| 看不到“资源市场”菜单 | 账号没有资源市场管理权限。普通用户应从“专家”或“技能包”中的对应入口使用已发布资源。 |
| 资源市场里看不到刚导入的包 | 资源还停留在草稿或审核中，尚未正式发布；也可能已经下架。 |
| 普通用户在技能市场看到空白 | 账号没有技能包权限，或当前没有已发布且上架的技能。联系管理员检查权限和资源状态。 |
| 可以看详情但无法创建专家 | 账号可能处于“仅使用分配专家”模式，或资源声明了当前安装器不支持的运行要求。联系管理员或资源维护人员。 |
| 安装技能时报同名冲突 | 系统不会覆盖已有技能包。换一个技能包名称，或先确认原包是否正在被其他专家使用。 |
| 安装后专家没有技能 | 只完成了“安装到技能包”，还没有在专家的“技能 → 技能包”页签打开挂载开关。 |
| 挂载开关不可用 | 当前 Agent 的存储后端不支持直接挂载技能包，可使用页面提供的“复制技能”能力。 |
| 发布新版本后旧 Agent 没变化 | 这是当前版本的预期行为。正式版本不可变，旧 Agent 和旧对话不会自动升级。 |
| 提示依赖不可用 | 依赖技能未发布、已下架、版本不匹配或内容摘要校验失败，需要管理员和开发人员共同检查依赖版本。 |
| 资源需要业务系统地址 | 业务系统地址是资源访问的现场 API 根地址，不是市场地址或模型地址。当前通用安装器不自动注入必填现场配置，需先完成适配或按现场配置流程处理。 |

## 八、试用验收清单

建议按以下顺序完成一次完整试用：

- [ ] 开发人员导入一个技能 ZIP，生成草稿并提交审核。
- [ ] 管理员查看草稿、预览文件并发布。
- [ ] 普通用户在技能包的资源市场看到该技能。
- [ ] 普通用户查看详情并选择一个正式版本。
- [ ] 普通用户将技能安装成新的技能包。
- [ ] 技能包详情显示正确的市场来源版本。
- [ ] 普通用户将技能包挂载到一个专家。
- [ ] 专家技能列表出现对应技能。
- [ ] 管理员发布技能新版本，确认旧技能包不会自动变化。
- [ ] 普通用户安装新版本并替换挂载，确认新版本可以独立使用。
- [ ] 管理员下架资源，确认新安装被阻止，已经安装的包仍然保留。
- [ ] 用无发布权限的普通账号验证：可以消费已发布资源，但不能进入发布管理操作。

如果需要导入外部开发的专家或技能，请先阅读[资源包开发规范](design/resource-package-development.md)。该规范定义 ZIP 目录、`market.json`、版本号、依赖和运行环境声明；它是资源能否导入本地市场的准入标准。
